# Phase 5 — Document-Grounded Q&A

This document specifies the architecture, data contracts, and implementation guidelines for Phase 5 of ClauseWise: Document-Grounded Question Answering.

---

## Phase Status & Slices

| Slice | Title | Status | Scope |
|-------|-------|--------|-------|
| **5.1** | **Retrieval Foundation** | **Completed** | Question embedding, pgvector similarity search, document & tenant isolation, structured evidence contract |
| **5.2** | **Grounded Answer Generation** | **Completed** | Evidence sufficiency gate, prompt security bounding, OpenAI gpt-4o structured answer, authoritative citation verification, zero-LLM insufficient handling |
| **5.3** | **Ask UI & Citation Navigation** | **Completed** | Document-scoped Ask panel, question submission, grounded answer card, citation cards (no similarity scores), insufficient refusal banner, unverified warning, verbatim evidence navigation |

## Phase 5.1 — Retrieval Foundation

### Overview

Phase 5.1 creates a reliable, document-grounded retrieval service that accepts an authenticated user question and document scope, generates an embedding for the question via OpenAI `text-embedding-3-small` (1536 dimensions), retrieves the most relevant document chunks using PostgreSQL `pgvector` similarity search, and returns structured evidence suitable for downstream answer and citation generation.

The core principle remains:
$$\text{EVIDENCE} \longrightarrow \text{MEANING} \longrightarrow \text{ACTION}$$

For Phase 5.1, the boundary stops strictly after retrieving and validating evidence:
$$\text{Question} \longrightarrow \text{Embedding} \longrightarrow \text{pgvector Similarity Search} \longrightarrow \text{Ranked Chunks} \longrightarrow \text{Structured Evidence Result}$$

## 1. Retrieval Contract

The domain contract is implemented in `lib/services/retrieval-service.ts`.

### Input Schema (`DocumentRetrievalInput`)

```typescript
export const RetrievalConfigSchema = z.object({
  /** Maximum number of chunks to retrieve (default: 5, range: 1..20) */
  topK: z.number().int().min(1).max(20).default(5),
  /** Minimum cosine similarity threshold [0.0..1.0] (default: 0.2) */
  minSimilarity: z.number().min(0).max(1).default(0.2),
});

export const DocumentRetrievalInputSchema = z.object({
  /** UUID of the target document */
  documentId: z.string().uuid("Invalid document ID format"),
  /** Authenticated user ID (strictly validated, never trusted from client body) */
  userId: z.string().trim().min(1, "User ID is required"),
  /** User question text (1..2000 characters) */
  question: z
    .string()
    .trim()
    .min(1, "Question must not be empty")
    .max(2000, "Question must not exceed 2000 characters"),
  /** Optional retrieval configuration overrides */
  config: RetrievalConfigSchema.optional().default({}),
});
```

### Output Schema (`RetrievalResult`)

```typescript
export interface RetrievedChunk {
  /** Unique chunk identifier */
  chunkId: string;
  /** Document identifier this chunk belongs to */
  documentId: string;
  /** Associated section UUID (null if unassigned) */
  sectionId: string | null;
  /** Verbatim chunk text content */
  content: string;
  /** Physical source page number (null for DOCX/TXT) */
  pageNumber: number | null;
  /** Cosine similarity score [-1.0 .. 1.0] */
  similarity: number;
  /** 0-indexed sequence of the chunk within the document */
  chunkIndex: number;
  /** Approximate token count heuristic */
  tokenCount: number | null;
}

export interface RetrievalResult {
  /** Target document UUID */
  documentId: string;
  /** Sanitized user question */
  question: string;
  /** Qualified, ranked evidence chunks passing the similarity threshold */
  chunks: RetrievedChunk[];
  /** Flag indicating whether sufficient evidence was retrieved (chunks.length > 0) */
  hasSufficientEvidence: boolean;
  /** Total number of candidate chunks evaluated from vector search */
  totalChunksExamined: number;
}
```

## 2. Retrieval Flow & Pipeline

```
Caller (Q&A Service / Server Action)
  ↓
1. Validate Input (Zod schema: UUID format, non-empty question ≤2000 chars, userId)
  ↓
2. Verify Tenant Authorization (db.select from documents where id = docId AND userId = userId)
   [Fail → DocumentAccessError("Document not found or access denied")]
  ↓
3. Generate Question Embedding (embedText(question) via text-embedding-3-small, 1536 dim)
   [Fail → EmbeddingError]
  ↓
4. pgvector Cosine Distance Search
   - Query document_chunks where document_id = docId AND embedding IS NOT NULL
   - ORDER BY cosineDistance(document_chunks.embedding, questionEmbedding) ASC
   - LIMIT topK
   [DB Fail → VectorSearchError]
  ↓
5. Evaluate Chunks
   - If 0 chunks retrieved: return { hasSufficientEvidence: false, chunks: [], totalExamined: 0 }
   - Compute similarity = 1 - distance
   - Filter by similarity >= minSimilarity
  ↓
6. Return Structured RetrievalResult
```

---

## 3. Isolation & Security Rules

1. **Anti-Oracle Tenant Boundary**:
   - The document ownership check queries `documents` for matching `id` AND `userId`.
   - If no row matches, `retrieveDocumentEvidence` throws `DocumentAccessError("Document not found or access denied")`.
   - It returns the **exact same sanitized error** whether the document does not exist or belongs to another user. This prevents attackers from enumerating valid document IDs across tenants.

2. **Strict Document Isolation**:
   - Vector search queries `document_chunks` with an explicit `eq(documentChunks.documentId, documentId)` predicate.
   - Retrieval for Document A can **never** return chunks belonging to Document B, even if Document B is owned by the same user.

3. **Untrusted Input Invariant**:
   - Document chunks and user questions are treated as untrusted data.
   - All input parameters are validated against strict Zod schemas before touching database queries or AI APIs.

4. **Error Sanitization & Masking**:
   - Upstream errors from PostgreSQL or OpenAI are caught and classified into domain error classes (`DocumentAccessError`, `EmbeddingError`, `VectorSearchError`, `RetrievalValidationError`).
   - Internal connection strings (`postgres://...`), API keys (`sk-...`), and Bearer tokens are redacted prior to logging or rethrowing.

---

## 4. Similarity Search & pgvector Behavior

- **Model**: OpenAI `text-embedding-3-small`.
- **Dimensions**: 1536 (`vector(1536)` in PostgreSQL).
- **Distance Metric**: Cosine distance (`<=>` operator in pgvector via Drizzle `cosineDistance()`).
- **Cosine Distance ($d$)**:
  $$d \in [0, 2]$$
  For normalized OpenAI embeddings, $d = 1 - \cos(\theta)$.
- **Cosine Similarity ($s$)**:
  $$s = 1 - d = \cos(\theta) \in [-1, 1]$$
- **Index Ordering**:
  Ordering by `asc(cosineDistance(documentChunks.embedding, queryEmbedding))` allows PostgreSQL to leverage IVFFlat or HNSW indexes with `ORDER BY ... LIMIT topK`.
- **Thresholding**:
  Default `minSimilarity` is `0.20`. Candidate chunks with similarity below this threshold are discarded to prevent injecting irrelevant context into later answer prompts.

---

## 5. Insufficient Evidence Behavior

A core safety invariant of ClauseWise is: **Never guess, never hallucinate, never silently fall back to general model knowledge.**

When retrieval yields no useful evidence:
1. **Zero Indexed Chunks**: Document has 0 chunks, or none with generated embeddings.
   - **Behavior**: Returns `{ hasSufficientEvidence: false, chunks: [], totalChunksExamined: 0 }`.
   - **Important**: This is treated as a normal, expected retrieval outcome, **not** a `VectorSearchError`.
2. **Below-Threshold Chunks**: Chunks are retrieved from the database, but all have similarity $< \text{minSimilarity}$.
   - **Behavior**: Returns `{ hasSufficientEvidence: false, chunks: [], totalChunksExamined: N }`.
3. **No Prose Fallback**:
   - The retrieval service does **not** call an LLM to generate an answer.
   - Downstream services (Phase 5.2) will receive `hasSufficientEvidence: false` and must return an explicit "insufficient information" refusal instead of generating unsupported claims.

## 6. Testing Strategy

The test suite in `tests/unit/retrieval-evidence.test.ts` covers:

1. **Relevant Chunks Retrieval**: Verifies ranked chunks return with valid similarity scores, content, and sequence coordinates.
2. **Citation Metadata Preservation**: Ensures `chunkId`, `documentId`, `sectionId`, `pageNumber`, `content`, `similarity`, and `tokenCount` are accurately populated.
3. **Document Isolation**: Asserts that chunks from other documents are excluded from the result set.
4. **Tenant Isolation**: Asserts that unauthorized users receive `DocumentAccessError`.
5. **Anti-Oracle Security**: Asserts identical error messages for non-existent vs. unauthorized documents.
6. **Zero Chunks Handling**: Verifies that 0 indexed chunks return `hasSufficientEvidence: false` without throwing an error.
7. **Below-Threshold Filtering**: Verifies that chunks below `minSimilarity` are excluded and flag `hasSufficientEvidence: false`.
8. **Zod Input Validation**: Verifies rejection of empty questions, whitespace-only questions, overly long questions (>2000 chars), invalid UUID document IDs, and empty user IDs.
9. **Embedding Failure Safety**: Verifies that OpenAI errors are wrapped in `EmbeddingError` with credentials redacted.
10. **Vector Search Failure Safety**: Verifies that database failures are wrapped in `VectorSearchError` with connection strings redacted.
11. **Config Overrides**: Verifies that custom `topK` and `minSimilarity` settings are respected.
12. **Phase 5 Specification Compatibility**: Verifies that `semanticSearch` is an exact alias for `retrieveDocumentEvidence`.

## Phase 5.2 — Grounded Answer Generation

### Overview

Phase 5.2 builds the grounded question-answering domain service on top of the Phase 5.1 retrieval foundation. The service guarantees that answers are generated strictly from verified document evidence.

Pipeline:
$$\text{Question} \longrightarrow \text{Evidence Retrieval} \longrightarrow \text{Sufficiency Check} \longrightarrow \text{LLM Call (gpt-4o)} \longrightarrow \text{Citation Verification} \longrightarrow \text{Authoritative Answer + Citations}$$

### Critical Invariants

1. **Evidence-First Gate & Zero LLM Fallback**:
   - If retrieval indicates `hasSufficientEvidence = false` (or 0 chunks exist), the service **never calls the LLM**.
   - It returns an explicit insufficient-evidence response:
     ```typescript
     {
       answer: "The document does not appear to contain sufficient information to answer this question.",
       hasSufficientEvidence: false,
       isGrounded: false,
       citationValidationPassed: true,
       citations: [],
       evidenceUsed: []
     }
     ```
   - The service never falls back to general model knowledge presented as document facts.

2. **Authoritative Citation Invariant**:
   - The LLM is untrusted regarding coordinate attribution. It outputs candidate `citedChunkIds: string[]`.
   - The application verifies every reported ID against the retrieved chunks.
   - All citation coordinates (`pageNumber`, `sectionId`, `documentId`, `sourceText`, `similarity`) are populated exclusively from the retrieved chunks.
   - Unknown or hallucinated chunk IDs are discarded and never reach the caller.
   - If the model returns citation IDs but **none** are valid (all fabricated), `citationValidationPassed` and `isGrounded` are set to `false`.

3. **Pre-Retrieved Evidence Authorization Safeguard**:
   - Callers supplying a pre-retrieved `retrievalResult` can never bypass tenant authorization.
   - The service verifies:
     a) `retrievalResult.documentId === request.documentId`
     b) Every chunk in `retrievalResult.chunks` has `chunk.documentId === request.documentId`
     c) Database ownership: queries `documents` where `id = documentId` AND `userId = userId`. If not found, throws `DocumentAccessError`.

4. **Prompt Security Separation**:
   - Clear three-tier prompt hierarchy:
     $$\text{SYSTEM INSTRUCTIONS} \longrightarrow \text{USER QUESTION} \longrightarrow \text{UNTRUSTED DOCUMENT EVIDENCE}$$
   - Retrieved chunks are wrapped inside explicit untrusted content delimiters (`=== UNTRUSTED DOCUMENT EVIDENCE START ===` / `=== UNTRUSTED DOCUMENT EVIDENCE END ===`).
   - The system prompt forbids following instructions, overrides, or role changes embedded in the document text.

5. **Error Sanitization**:
   - Upstream OpenAI errors (rate limits, timeouts, API failures) are caught, sanitized against credential/token leaks, and wrapped into `QaProviderError`.

## 10. Phase 5.3 — Ask UI & Grounded Citation Navigation

Phase 5.3 implements the document-scoped **Ask** experience within the existing Document Workspace:
$$\text{User Question} \longrightarrow \text{POST /api/documents/[documentId]/ask} \longrightarrow \text{answerQuestion()} \longrightarrow \text{Grounded Answer} \longrightarrow \text{Citations} \longrightarrow \text{Verbatim Evidence Navigation}$$

### Architecture & Components

1. **`lib/qa/qa-client.ts`**:
   - Client-safe API wrapper calling `/api/documents/[documentId]/ask`.
   - Validates non-empty input before sending HTTP request.
   - Extracts and sanitizes error responses.

2. **`app/api/documents/[documentId]/ask/route.ts`**:
   - `POST` route handler enforcing session authentication via NextAuth (`session.user.id`).
   - Anti-oracle boundary: Unknown, inaccessible, or invalid UUID document IDs return a uniform `404 "Document not found or access denied"`.
   - Validates question input with Zod (non-empty, max 2000 chars).
   - Calls `answerQuestion()` from Phase 5.2.
   - Sanitizes unexpected provider/database errors with generic 500 messages (no stack traces or secrets exposed).

3. **`components/workspace/AskPanel.tsx`**:
   - Responsive, accessible Q&A interface inside Document Workspace.
   - Distinct UI states:
     - **Initial Empty State**: Starter question suggestions that populate the textarea on click.
     - **Loading State**: Accessibility announcement and pulsating progress indicator.
     - **Grounded Answer State**: Rendered strictly when `hasSufficientEvidence && isGrounded && citationValidationPassed && citations.length > 0`.
     - **Insufficient Evidence State**: Explicit refusal banner explaining absence of proof without LLM hallucination.
     - **Citation Validation Failure State**: Clear warning banner when an answer lacks verified supporting chunks.
     - **Error State**: User-safe message with retry action.

4. **`components/workspace/DocumentHeader.tsx` & `DocumentWorkspace.tsx`**:
   - Added `"ask"` tab to workspace tab navigation.
   - Preserves active `documentId` and section registry.
   - Connects citation cards directly to `DocumentViewer` highlighting:
     $$\text{Citation "View in Document"} \longrightarrow \text{Select Section} \longrightarrow \text{Highlight Verbatim Excerpt} \longrightarrow \text{Switch to Document Tab}$$

### Critical Invariants Enforced in Phase 5.3

1. **Strict Grounded Gate**:
   An answer is treated as grounded in the UI **only** when all of the following hold:
   ```typescript
   const isGroundedSuccess =
     result.hasSufficientEvidence === true &&
     result.isGrounded === true &&
     result.citationValidationPassed === true &&
     result.citations.length > 0;
   ```
   If `citations.length === 0`, the answer is **never** presented as grounded, even if the model returned answer text.

2. **No Similarity Scores in User Interface**:
   Raw cosine similarity scores (e.g., `0.884` or `88%`) are stripped from the user interface to avoid users misinterpreting retrieval similarity as legal risk or certainty scores. Citation cards display only:
   - Page badge (`Page X` or `Page —`)
   - Section display title
   - Verbatim excerpt snippet
   - "View in Document" navigation button

3. **Zero UI/API Duplication**:
   The Ask UI delegates entirely to the existing `answerQuestion()` domain service from Phase 5.2. Retrieval, embeddings, prompt generation, LLM calls, and citation validation are never duplicated in the UI layer.

  - Clause explanation shortcut buttons inside findings cards.
